# **What still blocks 1.0:** 
* (1) I can’t verify **stage-level OpenLineage emission** in `PipelineBuilder`-docs promise it, but code shows partial wiring;
* (2) **module surfaces** still have elisions (`...`) and a few skeletons (e.g., `quality` empty while `quality-deequ` carries weight); 
* (3) **DQ story** is split (native checks vs Deequ); the docs and examples need to *pick one as default* and show the other as optional;
* (4) consistency & polish items (version labels, example runnable guarantees, “storage recipes” since you de-scoped bespoke S3/Azure).

---
## Below is the full, blunt pass with concrete fixes.


**Yellow (close, but tighten)**

* **Lineage “by default”**: you import/use `OpenLineageEmitter` and ship a Marquez Compose with docs, but I don’t see clear **per-stage** `START/COMPLETE/FAIL` emission in the builder (I see comments and pipeline-level mentions). Your docs promise “run → see lineage immediately.” Make that *true in code,* not just prose. OpenLineage/Marquez is the right backend. ([OpenLineage][10])
* **DQ story**: `quality-deequ` exists, but some code/tests lean on native Spark checks. Either (A) make **native Spark quality** the default and document Deequ as an optional runner, *or* (B) wire **Deequ 2.0.12 Spark-3.5** as the default for Spark runs and keep native checks as “no extra deps” mode. Align docs, examples, and build profiles to that choice. ([Maven Central][7], [Maven Repository][11])
* **Storage breadth**: you de-scoped bespoke S3/Azure (smart), but then **ship “storage recipes”**: S3A (`hadoop-aws`), ABFS (ADLS Gen2 via `hadoop-azure`), GCS connector. Provide copy-paste conf blocks and one “same pipeline, different URI scheme” example for each. ([Apache Hadoop][12], [Google Cloud][13])

**Red (must fix for 1.0)**

* **Elisions (`...`) in code/docs**: several Scala files and docs contain literal `...` placeholders. That’s a hard blocker for trust. Replace with complete code or delete the section.
* **Version claims vs status**: `docs/public-api.md` says “(v1.0)” while `VERSION_MANAGEMENT.md` points to `0.1.0-SNAPSHOT`. Label it **“Proposed 1.0 surface”** until you tag an RC.
* **Empty shells**: `modules/quality` is an empty scaffold while `quality-deequ` is active-either remove the empty module for 1.0.

### **Do-this-now fixes** (surgical, high impact)

1. **Wire lineage in the builder**
   In `PipelineBuilder.build` and/or `Pipeline.run`:

    * Emit **pipeline START** (one event), then for each stage emit **stage START/COMPLETE**, and finally **pipeline COMPLETE**; on any error emit **pipeline FAIL** with error text.
    * Make emission **best-effort** (don’t fail the data path on telemetry problems), but do log errors.
    * Point defaults to Marquez Compose (`OPENLINEAGE_URL=http://localhost:5000/api/v1/lineage`). ([OpenLineage][10])

2. **Pick a default DQ mode**

    * **Option A (simple default):** Native Spark checks (completeness/uniqueness/pattern) + optional Deequ profile runner.
    * **Option B (enterprise default):** Use **Deequ 2.0.12 for Spark 3.5** by default; keep native checks for lean builds. Update example deps and docs accordingly. ([Maven Central][7])

3. **Storage recipes page (required, since S3/Azure modules are de-scoped)**

    * One page with **S3A**, **ABFS/ABFSS**, **GCS**: jars, minimal config, and a single FlowForge pipeline switching only the URI scheme.
    * Cite the official Hadoop/Azure/GCS connector docs. ([Apache Hadoop][12], [Google Cloud][13])

4. **Delete/finish anything with `...`**

    * This includes docs and Scala sources with placeholder sections. Don’t ship ellipses.

5. **Lock the version story**

    * Mark `docs/public-api.md` as “Proposed 1.0 surface.”
    * In CI, produce a `0.9.0-RC1` draft release when the above three checkboxes are green.

* **Runtime enforcement** at sinks (Delta constraints) + optional DQ checks (Deequ).
* **Lineage by default** (OpenLineage → Marquez) to make runs visible with zero glue. ([OpenLineage][10])

**Where to go from here** (developer experience examples to highlight in docs):

* **“Drift demo”**: edit `id: Long` → `id: String` in `Contract.scala` → `sbt compile` fails with a helpful message → revert or adapt policy (`Exact` vs `Backward`).
* **“Double lock”**: add `NOT NULL` / `CHECK` on the Delta table; show a failing write if data breaks constraints. ([Delta Lake][5])

## Final, unpolished verdict

We’re in striking distance. The product feels coherent and opinionated in the right way. To credibly slap **1.0.0** on it:

* **Make lineage automatic in code**, not just in docs. (OpenLineage → Marquez.) ([OpenLineage][10])
* **Resolve the DQ default** and ensure examples + docs match your decision. (Deequ 2.0.12 Spark-3.5 exists; choose deliberately.) ([Maven Central][7])
* **Publish storage recipes** for **S3A / ABFS / GCS** since bespoke connectors are de-scoped. ([Apache Hadoop][12], [Google Cloud][13])
* **Delete or complete anything with `...`**, and remove any empty modules for 1.0.

Do that, tag **0.9-RC1**, and your “contract-first, effect-safe, Spark-honest” framework will stand out in a crowded space for a simple reason: **it refuses to compile lies**-and then backs that up at runtime with enforced constraints and visible lineage. That’s the combo others don’t ship.
