# FlowForge v1.0.0 readiness (updated 2026-10-06)

This document is the single source of truth for v1.0 readiness. Other documents should link here rather than
repeat a readiness claim, because a claim repeated in five places goes stale in four of them.

Nothing below is a promise about a date. It is a list of what works today, what does not, and what has to
change before the version number means anything.

## Where the build stands

- Scala 2.13.16 is the only version the whole build is cross-built for. `core` also builds and tests on
  3.3.6, which CI runs as `core/testQuick`. Nothing is cross-published, so the Scala 3 build comes from
  source.
- JDK 17 is the baseline. CI runs 17. Spark 3.5.x does not support a newer JDK.
- Spark 3.5.x is the engine that runs. `engines-spark/test` runs on every CI build; the Delta integration
  test is opt-in behind `-DwithSparkIT=true`.
- `filter`, `map`, `flatMap`, `runQualityChecks` and `profile` on Spark run over the whole DataFrame. They
  used to read `Dataset.data`, which is a sample of at most 100 records on a Spark-backed dataset, so a
  filter followed by a write wrote unfiltered rows and a violation in record 101 went unreported. The
  operations that read every record now carry a `DataDecoder` bound, which is what lets the engine push them
  into the frame.
- `engines-flink` builds and tests on Scala 2.13 against Flink 1.18. It used to be pinned to 2.12 for the
  Flink Scala API, which `core` does not publish for, so resolution failed before compilation started; the
  module now uses Flink's Java artifacts, which carry no Scala suffix. It was also missing from the root
  aggregate, so no build or test command reached it. `engines-flink/test` runs on every CI build and starts a
  local MiniCluster.
- `read`, `write`, `filter`, `map`, `flatMap`, `union`, `validate` and `runQualityChecks` on Flink run as
  batch jobs over every record. A Flink-backed dataset holds a plan rather than the records, so the driver
  keeps at most 100 of them.

## Blocking gaps

### Connector surfaces that are not implemented
Several connector paths exist as types without behaviour: the S3 read and write path on Spark raises a
failure, and the S3 connector body is commented out. The capability set advertises `Read` and `Write` without
saying which sources and sinks are covered, so a caller learns the gap at runtime. Capabilities should name
the sources and sinks, or the unimplemented ones should be removed from the public types.

## Known limits that are documented, not fixed

These are deliberate for v1.0 and recorded so nobody rediscovers them as bugs.

- `groupBy`, `join` and `sortBy` still run on the driver and so still see at most 100 records on a
  Spark-backed dataset. They were not part of the sample bug and are not pushed into the frame.
  `sortBy` takes an arbitrary `Ordering[K]`, which a frame cannot express, so that one needs a different
  signature rather than a different implementation.
- `validate` applies the contract to every record on both engines and reports an exact count of the records
  that broke it, but the list of distinct violation messages is capped at 1000. A message built from a
  record's own values is otherwise as large as the dataset. The cap cannot change `passed` or `score`, which
  come from the count. Every violation is reported as `Critical`: a contract is the shape the caller declared
  the data has, so the severity levels have no other source here.
- `DataProfile.nullCount` is always 0 on both engines. The field has no agreed meaning - records with a null
  field, or null records - and inventing one in the Spark engine alone would make the two engines disagree.
- When the Deequ module is on the classpath, `runQualityChecks` on Spark runs Deequ's `NotNull` constraints
  derived from the schema and does not evaluate the checks the caller passed. Without the module it evaluates
  the caller's checks over the frame.
- Streaming is not implemented. `DataAlgebra.stream` does one batch read and returns a single chunk. Nothing
  calls `readStream` or `writeStream` and Kafka is not a source `read` accepts.
- Engine parity is tested between Spark and the in-memory engine only, in
  `modules/engines-spark/src/test/scala/com/flowforge/engines/spark/EngineParitySpec.scala`. One divergence is
  pinned there: on an unsupported format Spark raises `DataProcessingError.ProcessingFailure` and the
  in-memory engine raises a plain `UnsupportedOperationException`. A caller that handles one does not handle
  the other.
- Flink parity is tested against the in-memory engine in
  `modules/engines-flink/src/test/scala/com/flowforge/engines/flink/CrossEngineParitySpec.scala`, with the
  same unsupported-format divergence pinned there.
- `groupBy`, `join`, `sortBy`, `take`, `drop`, `profile`, the CDC operations and the table operations still
  forward to the in-memory engine on Flink, so on a Flink-backed dataset they answer for at most the 100
  sampled records. They are the same operations that run on the driver for Spark, for the same reason.
- The Flink sink writes JSON and JSONL only. A dataflow sink cannot order a CSV header line ahead of the rows
  it writes, and a headerless CSV is a file this engine cannot read back, so a CSV sink raises rather than
  writing one. The sink runs at parallelism one so the output is the single file the caller named.
- Both engines hand every row to the caller's `DataDecoder` as JSON, including rows read from a CSV file,
  because JSON is the one representation the codecs and the engines both speak. A decoder that supports only
  one other format therefore decodes nothing, and the dataset's `data` is empty while its count is not. The
  decoder's `supportsFormat` is not consulted, so the caller gets no signal.
- A record count on both engines counts the rows the source holds, not the records that decoded. A file with
  rows the decoder rejects reports a count larger than the records anything can see, which inflates the
  denominator `validate` scores against. The in-memory engine counts decoded records instead, so the three
  engines agree only on a source every row of which decodes.
- The 1000-message cap on `validate` truncates deterministically on Spark, which orders by message before
  capping, and not on Flink, which has no cheap global sort over a `DataStream`. Which messages survive is
  unspecified there. On both engines the cap cannot change `passed` or `score`.
- The Flink engine runs batch jobs, not streaming ones. Every job sets `RuntimeExecutionMode.BATCH`, which is
  what makes a keyed count report one final value per key, and which means no unbounded source can be
  consumed. Every source it reads is a bounded file.
- Four `TODO` markers remain in `core`: record-level validation and the Reader-based pipeline in
  `syntax/PipelineSyntax.scala`, and the environment fallback and per-source loading in
  `algebra/ConfigurationAlgebra.scala`. Each one returns something rather than failing, so a caller gets a
  partial answer with no signal.

## How to close this out

The pass/fail list is in [release criteria](release-criteria.md). That page says what must be true to ship;
this page says what is true now. Each blocking gap above has a matching criterion there, so closing a gap
means a criterion flips, not that two documents have to be edited to agree.

One rule keeps it that way: a readiness claim lives here or links here, and nowhere else.
